## 0. 背景

### 为什么这是当前最高优先级？

PRD §4.1 定义的核心流水线：

```
上传素材 → 预处理 → AI 模型推理 → 绑定骨骼动画 → 输出 3D 模型
```

**这 5 个环节中，AI 模型推理是整个产品可行性的基石。** 如果照片→3D 宠物模型这条链路走不通，产品最核心的价值主张（"还原真实宠物"）就无法成立。

Sprint 1 的前端骨架和 3D 渲染管线已经验证完毕，但 AI 环节尚未触碰。在 Sprint 2（形象生成 MVP）启动之前，必须确认这个最大技术风险是可控的。

### 当前状态

| 已验证 | 未验证 |
|--------|--------|
| ✅ React + Tauri + Three.js 技术栈 | ❌ 照片→3D 模型 AI 方案是否存在 |
| ✅ 3D 渲染管线（R3F + 骨骼动画） | ❌ AI 生成模型的输出质量 |
| ✅ UI 页面骨架（创建/桌面/设置） | ❌ AI 模型与 Three.js 的兼容性 |
| ✅ 性能分级渲染 | ❌ 本地部署 vs 云端 API 的成本/延迟 |
| | ❌ "写实度控制" 的技术实现路径 |

## 1. 核心验证问题

### Q1：有没有可用的 AI 方案？

市场上是否有能"输入宠物照片，输出带骨骼绑定的 3D 模型"的 AI 服务/模型？

| 维度 | 云端 API | 本地开源模型 |
|------|---------|------------|
| 候选方案 | Meshy / Tripo / Luma AI / Rodin / CSM | TripoSR / Stable Fast 3D / InstantMesh / Wonder3D |
| 关键问题 | 对猫狗等动物的还原度如何？| 消费级 GPU（6-8GB 显存）能否跑？ |
| 评估方法 | 用真实宠物照片实测 ≥2 个方案 | 调研论文 + GitHub + 实测 |

### Q2：输出质量能否满足产品要求？

| 验证项 | 最低可接受标准 |
|--------|-------------|
| 几何还原 | 同品种宠物可肉眼区分（毛色、体型、面部特征）|
| 纹理质量 | ≥1024×1024 分辨率，无明显拉伸/接缝 |
| 模型格式 | GLB / GLTF（Three.js 原生支持）|
| 面数 | ≤50K triangles（可通过自动减面工具后处理）|
| 骨骼绑定 | 至少包含基础骨骼链（无骨骼则需评估 Mixamo 等自动绑定方案）|

### Q3：能否集成到现有技术栈？

| 集成点 | 验证方法 |
|--------|---------|
| Three.js `useGLTF` 加载 AI 生成模型 | 实测加载 + 材质/纹理检查 |
| 动画状态机映射 | 检查骨骼命名是否可映射到已有动画状态（idle/walk/lie_down 等 9 种）|
| 写实度控制 | 调研技术路径：shader 风格化（toon shading）？模型 LOD？混合方案？ |
| 性能 | 目标最低配置（GTX 1060 级别）实测渲染帧率 |

## 2. 验证任务分解

### Task 1：AI 方案市场调研

**负责人**：后端开发工程师
**产出**：AI 方案对比表

系统性地调研所有可行的图像→3D 方案，输出结构化对比：

| 字段 | 说明 |
|------|------|
| 方案名称 | 服务/模型名称 |
| 类型 | 云端 API / 本地模型 |
| URL | 官网 / GitHub |
| 动物支持 | 是否支持猫/狗等动物（多数方案以物体为主）|
| 输入要求 | 最少照片数、支持格式、分辨率要求 |
| 输出格式 | GLB / GLTF / OBJ / FBX / USDZ |
| 是否带纹理 | PBR 纹理 / 顶点色 |
| 是否带骨骼 | 有/无，若有则描述骨骼结构 |
| 面数 | 输出模型的 triangle 数量 |
| 速度 | 单次生成耗时 |
| 价格 | 免费额度 / 单价 / 月费 |
| 评分 | 1-5（宠物还原度维度）|

### Task 2：实测验证

**负责人**：后端 + 前端开发工程师
**产出**：实测截图 + 数据记录

从 Task 1 中选 **2 个最有希望的方案**，使用 3-5 张真实猫/狗照片走通完整链路：

1. **准备素材**：准备 3-5 张不同角度的猫/狗高清照片
2. **调用 AI**：分别用选定的方案生成 3D 模型，记录：
   - 实际耗时
   - 输出文件大小
   - 输出格式
   - 面数 / 纹理分辨率
   - 是否有骨骼绑定
3. **Three.js 加载**：在项目中加载生成的模型，检查：
   - 能否正常渲染
   - 纹理是否正确映射
   - 材质表现
   - 渲染帧率（中性能模式 30fps 目标）
4. **还原度评估**：与原始照片对比，主观评分（1-5）

### Task 3：集成方案设计

**负责人**：前端 + 后端开发工程师
**产出**：技术集成方案文档

基于 Task 2 的结果，设计集成架构：

1. **推荐方案**（本地/云端/混合）及理由
2. **集成架构图**：Tauri 调用链 + 数据流
3. **写实度控制**的技术路径
4. **异常处理**：AI 不可用时的降级方案
5. **成本估算**：免费额度 / 单用户成本 / 规模化成本

## 4. Go/No-Go 判定标准

| 判定 | 条件 |
|------|------|
| 🟢 **Go** | 至少 1 个方案能产出可识别品种的宠物 3D 模型，格式可被 Three.js 加载，可带骨骼或可后处理绑定 |
| 🟡 **Conditional Go** | 有方案可用，但存在可接受的限制（如：仅云端可用 / 面数偏高需后处理 / 还原度一般但可通过模板辅助改善）|
| 🔴 **No-Go** | 所有方案对动物（猫/狗）的还原度均不可接受，模型不可用或无法集成 |

### No-Go 时的 Plan B

| 降级方案 | 说明 | 用户体验影响 |
|---------|------|------------|
| **预置模板 + AI 纹理** | 预置多种猫/狗品种的 3D 模型，AI 仅从照片提取毛色纹理贴到模板上 | 品种特征保留，但非"独家还原" |
| **手动捏脸 + AI 辅助** | 用户选择品种/体型/毛色/花纹，AI 辅助生成纹理贴图 | 失去"照片自动还原"核心卖点，用户操作复杂度增加 |
| **纯云端高价方案** | 使用最贵的商业 API（如 Luma AI / Getty 3D）保证质量 | 成本高，可能需要向用户收费 |

## 5. 风险提示

| 风险 | 缓解措施 |
|------|---------|
| 现有 AI 方案以物体/人脸为主，对猫狗动物支持未知 | 优先测试声称支持动物的方案；实测多种动物照片 |
| 云端 API 可能有速率限制或地域限制 | 提前申请多个 API Key；准备代理方案 |
| 本地模型显存要求可能超出目标硬件 | 优先使用云端 API 作为主力方案，本地模型作为增强 |
| 生成的模型不带骨骼绑定 | 评估 Mixamo / AccuRIG 等自动绑定工具的可行性 |
